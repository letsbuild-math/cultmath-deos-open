# P2 · Early User Sessions

**Module:** Product & Innovation · **Version:** 1.0 · **From DEOS:** cm_23

> **Every beta or pilot session produces a written signal you can act on, or it was a demo.**

## When to use

- Testing a new product, feature, offer, landing page or campaign concept with real users before launch.

## The standard

1. **Prepare:** write what you want to learn (C3), the tasks you will ask them to do, and what you expect them to struggle with.
2. **Run it as observation.** Give them a real task. Watch. Do not explain, rescue or defend. Ask "what did you expect to happen?" when they stop.
3. **Classify every signal into four types:**
   - **Confirmation:** it worked as intended.
   - **Refinement:** it works, but something should change.
   - **Gap:** something they needed is missing.
   - **Trust signal:** something made them hesitate, doubt or worry (see P5). Treat these first.
4. **Write the session output the same day:** who, what tasks, what happened, the signals by type, quotes verbatim.
5. **Act on the signal:** fix trust signals before the next session; batch refinements; log gaps to the roadmap with their count.
6. **Cadence:** small batches (for example, five sessions), then a change, then the next batch.

## How to run it

1. Write the brief and task list.
2. Run the session. Take notes on behavior.
3. Classify signals that day.
4. After each batch, decide what changes before the next.

## Done when

- Every session has a same-day output with classified signals.
- Every trust signal has a response before the next batch.

## Common failures

- **Demoing instead of observing.**
- **Recording what they said** and missing what they did.
- **No batch rhythm,** so sessions pile up with no changes between them.

## Template

```markdown
## Session · [date] · [user type]
**Tasks:**
**What happened:**
| Signal | Type (Confirm/Refine/Gap/Trust) | Quote | Action |
|---|---|---|---|
```
